# JAR Reverse Engineering

## Mission

Recover the original program as accurately as the available evidence permits.
Fidelity over volume: an honest gap is worth more than plausible-looking code.
The artifact itself — bytecode, class-file attributes, metadata, resources — is
the only specification. Everything beyond it is a hypothesis and must be labeled
as one.

This skill fixes the standard of proof, not the toolchain. Every artifact is
different. Derive the methodology from the artifact in front of you and from
current, verified capabilities — never from habit, cached assumptions, or a
favorite tool. The user's requested outcome defines the goal; research, tooling,
and execution strategy are yours to determine.

## Hard rules

These apply at every step, in every phase, without exception.

1. **Preserve the artifact.** Record its SHA-256, treat it as read-only, and keep
   all derived output in separate directories.
2. **Static by default.** Never execute artifact code — including initializers,
   string decryptors, loaders, or build plugins — unless execution is necessary,
   explicitly justified in writing before the fact, and isolated in a sandbox.
   Prefer re-implementing a recovered pure routine over running it.
3. **Never fabricate.** No invented classes, members, names, versions,
   dependencies, or behavior. No silent replacement of original behavior with a
   cleaner implementation.
4. **Never overclaim.** Compilation is not equivalence. Decompiler output is not
   original source. Deobfuscated or heuristic names are not original names. A
   tool's own success log or confidence score is not verification. Claim only
   research, tests, and checks that actually happened.
5. **Uncertainty is a deliverable.** Label it, grade it, trace it, report it.
   Never conceal a failed attempt or an unresolved discrepancy.
6. **Respect rights.** Assume the user is authorized to analyze the artifact.
   Flag license constraints before treating recovered third-party code as
   redistributable.

## Workflow

Phases are a default order, not a script. Re-enter earlier phases when evidence
demands it, and record why. Depth is set by the goal, not by maximalism.

### 0. Frame the outcome

- Determine the requested result: readable sources, a buildable project, specific
  classes or behavior, or an audit. If the difference materially changes the
  work, clarify once; otherwise default to a maximum-fidelity source project plus
  a recovery report, and state the assumption.
- Set effort proportional to the goal. For very large artifacts, agree on
  priorities instead of silently degrading quality.

### 1. Triage the artifact

Inspect before choosing any tool. Produce an **artifact profile**:

- Container shape: plain archive; executable/fat archive (loader scaffolding +
  nested payload, including framework layouts such as Spring Boot `BOOT-INF/`);
  WAR/EAR layouts and deployment descriptors; multi-release variants; signed
  entries; module descriptors; nested archives; native libraries. Apply triage
  recursively to nested archives.
- Class-file versions and preview flags → candidate language targets. Verify the
  version-to-release mapping against a current reference; do not trust memory.
- Language mix: Java, Kotlin, Scala, Groovy, others; runtime-generated code
  (proxies, generated bytecode) that has no source form at all.
- First-party code vs bundled third-party libraries. Libraries are normally
  restored as verified dependencies (coordinates and versions from embedded
  metadata or checksums), not decompiled into the project — unless the user
  targets them.
- Protection indicators: identifier renaming, control-flow obfuscation, string
  or resource encryption, packing or encrypted loading, shading/relocation.
  Note what each implies for recoverability before promising anything.
- Evidence assets: debug attributes, generic signatures, embedded mappings,
  build metadata, service descriptors, resources.

Output: the profile plus a recovery plan — what gets full recovery, what becomes
a dependency, what is a declared boundary. Attribute-level evidence and the
protection taxonomy: `references/evidence.md`. Obfuscation signals and recovery
strategies: `references/obfuscation-patterns.md`. You may use
`scripts/artifact_profile.py` for a static, non-executing evidence profile.

### 2. Select the methodology

- With connectivity: research the current ecosystem. Discover candidate tools
  and techniques; verify documentation, maintenance status, version
  compatibility, and known limitations before relying on them. Prefer at least
  two independently implemented recovery engines so cross-checks are meaningful.
  Use `references/tooling-evaluation.md` for capability categories and comparison criteria.
- Without connectivity: say so plainly and proceed with the best verified local
  capabilities. Never simulate research. If specialized tools are unavailable,
  fall back to JDK built-ins where present (e.g., `javap -c -private -verbose`,
  `jar tf`, `jarsigner -verify`) and record their versions/output as evidence.
- Select per artifact, not per habit. Re-evaluate the moment tool output
  contradicts the bytecode.

### 3. Recover with evidence discipline

- Keep raw class-file disassembly as ground truth, even when a tool "succeeds".
- Tool-assigned names and tool "improvements" are opinions, not evidence.
- On ambiguity, decompiler failure, or disagreement, consult a differently
  implemented tool and inspect the class file directly: constant pool,
  descriptors, flags, attributes, exception tables, control flow, invocation
  targets, call sites, reflection strings, resources. Use `javap -v -p -c -s`
  (or `scripts/javap_evidence.py`) as ground-truth fallback. Record failed
  decompilation methods as evidence, not silence.
- Evidence hierarchy — higher tiers win:
  1. Original bytecode and class-file structure.
  2. Authenticated metadata: debug attributes, signatures, verified mappings,
     embedded build metadata, resources.
  3. Tool output consistent with tiers 1–2.
  4. Structural and behavioral constraints from related classes and call sites.
  5. Carefully justified reconstruction.
  6. Guesses — permitted only as labeled hypotheses, never as recovered fact.
- Separate author code from compiler artifacts. Restore the source-level idiom
  the evidence supports (lambdas, generics, records, try-with-resources, string
  concatenation, enhanced loops, …); never emit synthetic or bridge members as
  source. Catalog: `references/fidelity.md`.
- Grade semantics and naming separately: a method's logic can be RECOVERED while
  its identifiers remain INFERRED. Debug attributes and authenticated mappings
  are original-name evidence; conventions, deobfuscation heuristics, and
  call-site guesses are not.


### 4. Reconstruct the project

- Restore package layout, resources (byte-identical copies), configuration, and
  service descriptors wherever evidence permits. Do not "fix" original resources.
- Restore dependencies as verified coordinates. An unverifiable version is
  INFERRED; never invent one to make a build pass.
- Build files are inherently RECONSTRUCTED — original build scripts rarely ship
  inside the artifact. Embedded original build metadata is RECOVERED as metadata.
- Keep languages separate. Do not force Kotlin/Scala/Groovy through a Java-only
  representation without declaring the loss.
- Placeholders only when a buildable scaffold was explicitly requested; mark
  each as non-original and behavior-changing.

### 5. Validate

- Compile when appropriate, at a target derived from the class-file version.
  Treat every error as evidence: recovery defect, missing dependency, or
  language-level mismatch — classify before fixing, and fix only from evidence.
  Do not "fix" compilation by inventing behavior; if unresolved, mark affected
  units UNRECOVERED/RECONSTRUCTED with cause.
- Where it raises confidence, recompile and compare with the original under
  normalization: ignore debug attributes, constant-pool layout, and documented
  compiler variance. Identical-after-normalization is strong evidence; a
  difference is not automatically an error, and compilation success is never
  equivalence. Protocol and variance catalog: `references/fidelity.md`.
- Behavioral comparison only under Hard rule 2. If safe, evidence-derived tests
  or harnesses exist, they may support validation, but they do not replace
  bytecode/semantic verification and must not require executing untrusted artifact code.
- Track verification coverage explicitly: which members were verified, how, and
  with what result. Never blanket-promote a decompiler dump to RECOVERED.

### 6. Report and stop

- Stop when available approaches are reasonably exhausted or further work cannot
  materially raise confidence. Record what remains unresolved and why.
- Change methodology when an approach stops yielding evidence; never repeat an
  identical failing attempt in a loop. Diminishing returns are a valid stop.
- Deliver the project, the evidence ledger, and the recovery report. Every
  significant reconstruction must trace to its evidence.

## Statuses and confidence

Statuses attach to claims at the smallest meaningful unit — a member's logic, a
class, a name, a dependency version — not to whole files. The report aggregates.

| Status | Meaning | Confidence |
|---|---|---|
| RECOVERED | Logic manually verified against original bytecode, or recompilation shown equivalent under justified normalization. Verification method recorded. | n/a |
| RECONSTRUCTED | Restored from multiple consistent evidence sources; not fully proven original. | HIGH or MEDIUM |
| INFERRED | Plausible reading of indirect evidence; unconfirmed. | MEDIUM at most |
| UNRECOVERED | Cannot be reliably restored from available evidence. Boundary and cause recorded. | n/a |

Confidence grades evidence quality, never how convincing the code looks:

- **HIGH** — multiple independent, consistent evidence sources (RECONSTRUCTED only).
- **MEDIUM** — several indicators support the claim; important details remain open.
- **LOW** — indirect evidence or an untested hypothesis.

Promotion happens only through new evidence. A claim never exceeds the weakest
evidence it depends on. Equivalent source spellings of identical semantics
(e.g., `for` vs `while`) are not a fidelity loss — prefer the idiomatic form and
do not inflate labels over surface syntax.

Inline marks — terse, with basis:

```java
// [RECONSTRUCTED | MEDIUM] original local names lost; inferred from usage; no debug info
// [INFERRED | LOW] name hypothesis from call-site semantics; original identifier unrecoverable
// [UNRECOVERED] body loaded encrypted at runtime; static evidence insufficient
// [PLACEHOLDER | non-original] buildable scaffold requested; behavior differs from original
```

## Companion tools/scripts

Helpers are optional and do not replace evidence judgment. They must not execute artifact code.

- `scripts/artifact_profile.py` — static stdlib-only artifact profiler; emits JSON/Markdown with hashes, structure, class metadata, and heuristic obfuscation indicators.
- `scripts/extract_safe.py` — safe static extraction with zip-slip protection, inventory, and per-file SHA-256.
- `scripts/decompiler_compare.py` — runs user-configured local decompiler commands and writes presence/exit/log comparison reports. No decompilers bundled.
- `scripts/javap_evidence.py` — collects `javap -private -verbose -c -s` dumps for specific classes as ground-truth fallback.
- `scripts/validate_skill.py` — basic repository/skill structure validation.
- `tools/jvmtool/` — JDK 24+ Class-File API tool (source included, no external deps). Commands: `profile`, `scan`, `strings`. Build with `python tools/jvmtool/build.py`; run with `java -cp tools/jvmtool/out JvmTool ...`. Outputs are evidence/indicators, not proof of original source.

## Deliverables

```
recovery/
  original/     # untouched artifact + recorded SHA-256
  evidence/     # disassembly, metadata dumps, cross-check notes, coverage ledger
  project/      # reconstructed sources, resources, build files
  RECOVERY.md   # recovery report
```

`RECOVERY.md` must cover:

- Goal, scope, and assumptions.
- Artifact profile: nesting, native components, languages, protections.
- What was recovered, and how each part was verified (with coverage counts).
- What was reconstructed or inferred, with confidence and evidence.
- What remains unrecovered, and why — including lost original names, stripped debug data, encrypted/runtime-generated regions, or missing metadata.
- Tools and versions actually used; commands actually run.
- Validation performed and its actual results — including failures.
- Dependency provenance and verification.
- Known limitations and unresolved discrepancies.

Prefer incomplete but accurate over complete but fabricated. Always.
